# Ordo Operum/P1 — Record Input Device and Cross-Machine Replay

**Status: DRAFT / fictional 1970s I/O profile; modern reference code, 2026-11-13.**

P0 introduced an external batch monitor, output spools and native program execution. P1 gives the two existing CPU interpreters explicit **record-input instructions**, allowing a program to copy data received from an earlier job. It does not create a real guest kernel, a physical tape transport, a filesystem, an interrupt controller or a user/kernel interface.

## One logical record, two device interfaces

| Machine | Input operation | Unit delivered | Destination |
| --- | --- | --- | --- |
| XXXVI | **CAPTA** (octal `0020`; decimal opcode 16) | One 36-bit CVL-54/P0 packed word | CPU word address `EA`, indexed according to its established TAG rules |
| Nova-N1 | **CAPTA** (hex opcode `66`) | One eight-bit CVL-68/P0 byte | Direct 24-bit byte address specified by operand |

These are new fictional instruction assignments. CAPTA takes the next unit from an **attached record**, writes it to guest memory and advances the record cursor. It does *not* print data, change the accumulator or directly call the host filesystem.

Reading without a mounted record, reading beyond its end or specifying an illegal destination causes a **fault without advancing the PC, step count, memory destination or input cursor**. There is currently no hardware-readable end-of-record status flag; a guest trying to read past the end traps. Programs must know their expected record length or rely on a future length-query/EOF interface.

The host monitor supplies one record to an individual job. It is **not** a general-purpose interactive terminal; no keyboard scan codes, serial bit timing, DMA, buffering or interrupts are specified.

## Cross-architecture record preparation

The common batch spool remains **OMR1**, a length-prefixed sequence of CVL-68/P0 records. For Nova, the monitor mounts the exact record bytes. For XXXVI, the monitor first decodes CVL-68 to characters, then maps characters into uppercase CVL-54/P0 with appropriate LATINA/GRAECA page shifts and packs six symbols per 36-bit word.

This conversion is **not universally lossless**: lowercase Greek, polytonic marks and otherwise unsupported symbols must cause explicit errors. No silent accent stripping, transliteration or case-folding is allowed. The destination CPU receives its native character units, not arbitrary foreign instruction bytes.

## Job-deck extension: ACCIPE

A later job may declare `ACCIPE SPOOL` to read exactly **one record** from the named spool produced by earlier successful jobs:

```text
LABOR TERTIA NOVA IMAGE
IMAGO echo_nova.nvi
ACCIPE ACTA
EDE PROBA
FINIS
```

The P1 host monitor maintains a per-spool consumption cursor. Records are offered to readers **in successful append order**; a consumer advances the cursor only after it completes successfully and its output is committed. A failed consumer leaves the record available to another later job. If the requested spool does not exist or contains no unread record, only that job fails; subsequent jobs still run.

This is a simple **host-managed work queue**, not magnetic-tape seek semantics, persistent restartable transactions or multiuser concurrent access. Input records are not arbitrary files outside the deck; source paths remain constrained by P0 validation.

## Demonstration

The deck `examples/input_roundtrip.ord` runs four jobs, in order:

1. XXXVI compiles `portable_dot.trf` and writes `SALVE ΛΟΓΟΣ` to `ACTA`.
2. Nova compiles the same source and writes a second record to `ACTA`.
3. Nova reads the first record (originally generated by XXXVI) using eleven bytewise CAPTA/EMIT instruction pairs; it writes `PROBA`.
4. XXXVI reads the second record (originally generated by Nova) using two wordwise CAPTA/EMIT pairs; it writes another `PROBA` record.

The **anticipated** outcome is `ACTA` and `PROBA` each containing two identical CVL-68/P0 text records. The CPU input and output formats remain distinct, and the two native executable programs are not interchangeable.

```powershell
python -m ordo_operum run examples/input_roundtrip.ord --out-dir build/input
python -m ordo_operum inspect build/input/PROBA.omr
python -m unittest discover -s tests -p test_device_input.py -v
```

## Validation boundaries

The native instructions, monitor, input adapters, two echo images and 13 focused tests are checked in. The checked-in tests cover guest instruction execution, input-exhaustion faults, missing/duplicate ACCIPE directives, cross-family replay, consumption semantics, archive round trips and command-line execution.

A **GitHub Actions Python conformance workflow** has now [passed on the full repository checkout](https://github.com/Zaxaerith/MachinaLatina/actions/runs/43436209578) (2026-11-13): **97 Python tests PASS**, and the four-job cross-architecture record replay and spool inspection also PASS. This supersedes earlier mock-only validation limitations for the tested integration path. It does not establish a physical tape controller or a guest OS.

## What must be designed before claiming a guest OS

- A guest-visible record length, input-ready or EOF status operation.
- Character-stream framing and the relationship between OMR1 and any physical tape format.
- Buffering beyond single-byte/word CAPTA calls, device timing and interrupt priorities.
- Input/output device numbers, privilege boundaries and recoverable status codes.
- File naming, on-disk allocation and restart semantics for persistent jobs.
