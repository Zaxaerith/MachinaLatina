# CVSTOS — Distribution, Device Trust and Energy Policy
> DRAFT · 2026-11-26. Proposed 2011–2026 policy profiles, not a complete package binary format, cryptographic standard, scheduler implementation or historical product.

## 1. Package identity is not app permission
Candidate package descriptor (logical fields, no canonical serialization yet): publisher public-key identity; stable nonzero package ID scoped to publisher; release counter u64; target ISA/mode, OS ABI and required extensions; runtime profile; component list with exact byte lengths and content digests; requested capability classes; COS display names and registry release; source/build provenance when supplied. A signature covers a future canonical manifest plus component identities; cryptographic algorithm, trust-chain format and parser are deliberately unspecified. Signature validity authenticates a declared publisher under configured policy, not absence of bugs or malicious behavior. The store review is an additional decision. Installation grants no device permissions automatically. User-facing labels must distinguish visually confusable Latin A and Greek Α; stable package identities remain separate. No requirement that every language use a Latin transliteration for its display title.

Updates require verified publisher continuity, same package identity, compatible target and increasing release counter; rollback requires an explicit recovery policy, not an ordinary update. Key rotation/recovery and emergency revocation require separate authenticated protocols. Preserve app data only under verified identity continuity; newly requested permissions are ungranted until consent/policy. No signature bypass through document attachments or passive NODVS.

## 2. Two independent trust decisions
- APPS: vendor-certified store, independent signed repository, or locally signed package explicitly approved by user under device policy. All obey the same runtime sandbox. Proposed open-owner profile permits adding user-managed publisher keys; closed managed profile restricts trust roots, with the restriction disclosed.
- BOOT: vendor-controlled boot, or owner-enrolled OS signing key on supported devices. Owner enrollment requires physical confirmation, clear data-risk notice and fresh enrollment of trust roots; preserve existing data only if a defined secure migration permits it. App signing never implies permission to replace OS or baseband firmware. Measured/verified boot, secure storage, key handling and rollback protection are separate hardware/protocol work, not implemented here.

Recommended historical branch: 2014–2018 controversy yields CVSTOS LIBER-oriented owner-controlled devices coexisting with locked commercial models. LIBERTAS CODICVM asks for installability, documentation, long-term updates and exportable archives. Open code alone cannot unlock boot, and user-controlled signing need not mean disabling verification. Actual licenses remain undecided; real repo MIT/CC BY 4.0 unchanged.

## 3. Resource sessions and application lifecycle
Candidate foreground, background, suspended, terminated states. Foreground is determined by trusted compositor/user session, not application assertion. Background transition invalidates foreground-only grants, stops ordinary foreground device sessions before further delivery and cancels associated pending tasks. Resume requires a newly valid grant/session; explicitly approved background navigation is a separate scope with visible status and user stop action. Camera/microphone/location are separate classes; no blanket device privilege. SERMO CLIENS-style handlers may use broker capabilities but cannot obtain them from a text literal.

Illustrative scheduling policy: separate CPU quota, network-byte quota and wakeup quota per installation/profile in a fixed 60-second monotonic accounting window anchored to system boot. For an ordinary approved background task choose 2 CPU-seconds, 256 KiB combined application payload sent/received via broker, four broker-triggered background task activations per window. CPU usage is total measured core execution time across all app threads, not wall time or energy. CPU preemption stops further execution when depleted subject to platform accounting granularity; device or network work must be separately reserved/limited. Bytes count at broker admission/delivery, not all modem airtime; retries and radio overhead need separate accounting. Reserve against quota before accepting work, reconcile actual consumption, no negative counters; pending tasks deferred until a new window or user foreground grant, not silently executed. This is illustrative policy, not universal battery savings or specified hardware timer. No banking unused quota, no resetting by killing/restarting app, no implicit quota for suspended apps. Critical system calls, accessibility and emergency services need separately governed policies; no general user-app bypass.

Example background task uses 1.5 CPU-seconds, 192 KiB and three activations. Remaining 0.5 CPU-seconds, 64 KiB and one activation. A request needing 96 KiB cannot be admitted in this window even if CPU time remains. Foreground transition changes applicable policy but does not refill background quota. Actual energy depends on radio, display, SoC state and workload. Later accelerators require separate accounting, data isolation and cancellation semantics.

## 4. Offline and AI
An offline NODVS cache is scoped to installation/user and authorization context; cached content is not automatically eligible for a new principal. Revocation denies later broker reads, not already exported copies. Offline validity/expiry and sync conflict policy need a later standard. In 2021–2026 candidate devices, local inference may operate on user-selected documents under separate model/accelerator grants; uploading document data is a separate network decision. NODVS is not executable model instructions; model output does not inherit source authority. No asserted local model performance, token efficiency or energy benchmark.
