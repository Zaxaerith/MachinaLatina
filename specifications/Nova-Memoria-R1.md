# Nova Memoria R1 — Memory-centred heterogeneous platform
> FUTURE SCENARIO / DRAFT / NOT CANON · 2026-11-26. Candidate 2030–2035 platform, not a shipped CPU, fabricated chip, measured system, or complete ISA.

## 1. Architectural direction
Preserve Nova Magna M64's 64-bit registers, low 48-bit byte addresses and big-endian external conventions where supported; no new instruction encoding is assigned. Actual M64 privilege, procedure ABI, multicore atomics and device isolation remain open (C19/C23). Memoria is a platform name, not a claim of binary compatibility. Proposed components: Nova host cores for control, FIGVRA descendants for graphics/parallel tasks, MATRICES engines for neural algebra, optional Sextaria-inspired scientific engine, memory controllers, and a trusted resource broker. Devices may use different internal words and ISA. On-package chiplets and stacked memory are plausible design options, not required manufacturing technologies or proof of cost/thermal advantage.

Candidate physical tiers: on-die scratch/cache, high-bandwidth package memory, larger system RAM, persistent storage. Capacity, latency, bandwidth and energy per moved byte differ; persistent storage is not ordinary coherent RAM. A shared allocation can be physically resident on one tier, migrate or need a copy. Uniform resource identity is not uniform access time. Coherent CPU caches may be assumed for a later full platform, but R1 device sharing uses explicit ownership rather than a universal hardware coherence promise.

## 2. Logical buffer contract
R1 is an abstract, single-host, asynchronous service model. It does not modify earlier synchronous MATRICES/FIGVRA profiles. Broker creates nonzero u64 object ID scoped to boot/session; never reuse in that scope. Each allocation has length 1..2^30 octets, schema/profile, owner principal, state, and nonzero u64 generation. Offsets and lengths are u64; validate full span by checked arithmetic. Client handles are process-local and do not contain physical addresses. Device submission binds object identity, generation, range, operation and endpoint. No pointer guessed from a numeric ID is authoritative. All applications/devices need independently mediated access; no raw DMA by untrusted apps.

Ownership is for a whole allocation (even a subrange operation). No overlapping device access, read sharing, aliases with independent lifetime, or concurrent CPU/device mapping in this deliberately conservative baseline. States HOST, DEVICE_READ, DEVICE_WRITE, READY, INVALID. HOST: only owning authorized host can access bytes. To submit, revoke host mapping, complete outstanding host accesses, make input bytes visible to device; broker then installs bounded device mapping and marks DEVICE_READ or DEVICE_WRITE. All state transitions serialized by broker. Transfer across physical memories, if needed, occurs under broker control. Hardware must prevent unauthorized DMA and stale mappings; if such enforcement cannot be provided, use isolated copied buffers or deny submission. Resource grants and lifetime remain separate from address translation.

DEVICE_READ permits device read of authorized range only. DEVICE_WRITE is exclusive read/write of authorized range, including reads for read-modify-write; other ranges inaccessible. Output bytes are not host-visible until completion. For operations promising transactional output (e.g. MATRICES R1), write a separate private output allocation and publish only on success; no in-place rollback promise. Completion requires device work stopped, device writes visible, device mapping removed, outstanding accesses drained; success enters READY. Host ACQUIRE checks active grant and generation, transfers ownership to HOST and increments generation. Old-generation tickets fail; counters never wrap, retire exhausted object. If device failure or uncertain completion, mark INVALID and deny access; quarantine backing storage until device access is reliably stopped and mappings drained, then sanitize before reuse. Cancel request does not guarantee instantaneous termination. A completion from a stale ticket cannot release a newer allocation. Crash recovery and distributed memory excluded.

| State | Host access | Device access |
| --- | --- | --- |
| HOST | read/write within grant | none |
| DEVICE_READ | none | read only, granted span |
| DEVICE_WRITE | none | read/write, granted span |
| READY | none until ACQUIRE | none |
| INVALID | none | revoked; quarantine if not confirmed stopped |

A host and device may optionally map an allocation at the same 48-bit virtual address if a future translation profile supports it. Such equality is not authorization, coherence, or a physical-location guarantee. R1 interoperates through handles; it defines no MMU/IOMMU page table, fence instruction, cache maintenance opcode, driver ABI or memory consistency model for concurrent accesses. These are prerequisites for implementation.

## 3. Paper fixture
Object 42 generation 7 in HOST, length 131072 octets. CPU writes a 256x256 M16 matrix. Submit read-only to one MATRICES device; CPU access denied during DEVICE_READ. Successful completion with mappings drained -> READY; host ACQUIRE -> HOST generation 8. Old generation 7 submission denied. If device loses contact, INVALID instead of READY; storage quarantined. This is a logical trace, not executed code. A real MATMUL needs two separately granted inputs and a separately staged output; fixture demonstrates only one input's ownership.

## 4. Data movement accounting
For a dense 8-billion-parameter model at 4 bits per weight, packed weights = 4e9 octets (3.73 GiB) excluding scales/cache/runtime. Under illustrative batch-1 autoregressive decoding that reads all weights once per generated token from the selected memory tier, ideal bandwidth-only ceiling B/4e9 tokens/s: 128 GB/s -> 32; 512 GB/s -> 128; 1024 GB/s -> 256. Decimal GB/s; no guaranteed achievable throughput. Caches, reuse, sparse activation, batching, compute, KV traffic, synchronization and actual device efficiency change the result. Two separate 4 GB weight copies require 8 GB payload storage; a genuinely shared physical allocation can avoid duplication but not necessarily interconnect reads. No benchmark or performance forecast.

Near-memory operations (filter, scan, reduction) may reduce bytes crossing host interconnect. For an ideal 1 GiB scan returning 1 MiB, output payload crossing host link is 1/1024 of input if resident there and the operation needs no other transfer. Input ingest, command metadata, internal memory reads and coherence are excluded; computation does not become free. In-memory arithmetic remains a separate research branch with precision, endurance, temperature and manufacturing constraints.
